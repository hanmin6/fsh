# 客户公司检索与五级评级

用户授权将历史客户显示在“客户与评级”，调用现有大语言模型结合聊天历史与公开公司资料完成五级评级，并自动处理以后新增客户。

## 行为

- 客户列表默认显示潜在客户（Lead），历史导入客户直接可见；公司、联系人仍可切换。
- 保持已有等级代码兼容：S=超高、A=高、B=中、C=低，新增 D=超低。所有选择器及评级标识显示中文。
- 评级衡量采购潜力、需求匹配和跟进价值。信息少、未回复或公司无法核实本身不构成低评级理由。
- 使用正式配置中的 GPT 文本模型（当前 `gpt-6.1-sol`），第一阶段实际调用联网搜索并收集引用，第二阶段读取历史资料、检索报告与已验证 URL 生成结构化评级。
- 保存评级理由、证据消息、公司匹配情况、公开来源、下一步建议、模型和时间。只有检索工具返回的来源 URL 可以保存为证据；同名匹配不能确认公司。
- 手工调整保存为 `ratingSource=manual`，自动结果仍保留在 AI 字段，但不覆盖人工等级。
- 新 Lead、Account、Contact 默认待评级。原生 `FusanheCustomerRating` 定时任务每分钟扫描，默认每次处理 1 位；每客户文件锁防止重复付费请求。失败最多尝试 3 次，延迟重试；过期运行状态可恢复。
- 不会生成回复草稿或发送任务。

## 主要实现

`CustomerRatingPolicy.php` 定义评级标准、公司匹配及证据校验；`TextGateway::research` 执行带真实搜索证据的双阶段分析；`CustomerRatingService.php` 维护任务状态与写入；`Classes/Jobs/CustomerRating.php` 接入 Espo 原生调度。三种客户实体的 `RecordRating` 共用字段保护。前端 `customer-rating.tsx` 展示证据和来源。

模型上游当前不接受 `max_tool_calls`；不发送该参数。搜索阶段使用标准引用文本；结构化输出阶段独立调用 JSON 模式，避免 JSON 结果缺失引用元数据。不会静默替换模型。搜索次数通过提示约束，不视为硬性费用上限；保留服务方返回的 token 使用量。

历史上下文最多 150 条且有输入长度限制，发生截断时在详情显式提示。公司确认还需原始历史中的公司名或域名与有引用的官网对应；无法满足时降为候选。评级是当前证据下可修正的业务判断。
